# Evidence behind the checklist

Measured on Linux, WSL and Windows hosts between 2026-09-01 and 2026-10-14.
Three rows were measured again on 2026-11-12; [Rerun on Node 26.13.1](#rerun-on-node-26131)
gives those figures and how the runs differ from the first ones.
Every figure names its workload and its count where the source recorded them.
[Tested versions](#tested-versions) lists the SQLite, driver, runtime and operating
system versions recovered from the records of each measurement. Where a version
could not be recovered, the table says "Not recorded".
**M** means measured here, **D** means read from the SQLite documentation,
**U** means unconfirmed. Treat a figure as one workload's result, not a
benchmark.

## Rerun on Node 26.13.1

Three rows above were measured again on 2026-11-12 with Node 26.13.1, whose bundled
SQLite is 3.54.1 (read with `select sqlite_version()` in every run). The first runs
were on Linux under WSL2 (ext4 on a virtual disk), Node 26.11.1, SQLite 3.53.4 and a
15.2 GB copy of an application database. The rerun was on native Linux (xfs on an
NVMe disk) against the live file of the same application, 13.9 GB, with a writer
running. Host, disk, file system and data all changed with the versions, so a gap
between a first figure and a rerun figure cannot be assigned to Node or SQLite. No run
on Node 26.11.1 was made on the new host. Hyperfine 2.0.0 timed whole commands and
Tinybench 6.2.2 timed operations. Variation is (maximum minus minimum) over the median
of the runs, and above 25% counts as flagged. **M** applies to every figure below.

Workloads, in the order of the table:

- **Planner.** The old turn-start node query of the application, a reused prepared
  statement on a read-only connection to a `backup()` copy of the live file, with
  statistics deleted from the copy for the first arm. Each cell is the median of 5
  fresh processes (Tinybench, 300 ms after 100 ms of warmup). The threads were the
  three with the most nodes (44,057, 16,831 and 14,916) and one with 40, each with its
  last run by run id. The first run's plan used `orchestration_v2_projection_nodes_thread_run_idx`;
  the no-statistics plan now uses `orchestration_v2_projection_nodes_settled_leaf_idx`,
  so the application's schema differs from the first run's. The live file has an
  empty `sqlite_stat1`. SQLite 3.54.1 has a reported regression in which a query with
  many common table expressions fails the expression-depth check (workerd pull request
  8347); this query has no such expression, so the row does not test it.
- **Synchronous.** Batches of 1,000 commits (`BEGIN IMMEDIATE`, one 3,000-character row
  and one index entry, `COMMIT`) in WAL mode, on the disk that holds the live file. One
  fresh process and database per run, one warmup batch and 10 timed batches, 5 runs per
  arm, alternating. A batch's milliseconds equal the microseconds per commit; the figure
  is the median of the run medians.
- **Copy.** Whole commands, 3 rounds with the order alternating, one run per arm per
  round, each output deleted after its run. `backup()` ran in one step. The file cache
  was not dropped, so after the first read the source came from memory (770 KB read from
  disk in the last attempt). The `backup()` copy made for the planner row passed
  `quick_check`; the timed outputs were deleted after each run and not checked.

Admission: each phase ran under the host benchmark lock, in its own cgroup, with the
continuous observer. The planner arms passed. The synchronous and copy phases and the cold
optimize were rejected by the observer only for the workload's own I/O pressure (385, 123
and 647 ms of full stall in an interval, against 100 ms; the host's was no higher than the
workload's), which a unit made of fsyncs or a 14 GB write produces by itself. Two earlier
attempts, rejected for 54 MB of host swap-out (copy) and 13.8 ms of host memory pressure
(first optimize), were rerun and their receipts kept.

## Claims that did not hold

These appeared in transcripts or records and were withdrawn, disproved or never
confirmed. Do not repeat them without re-measuring.

- **"`busy_timeout` does not cover `journal_mode`."** A 400 ms hold was waited
  out in 429 ms. The failures came from a zero timeout, or from several
  processes converting a new file at once.
- **"A database-is-locked failure was fixed with a busy timeout and
  `BEGIN IMMEDIATE`."** One indexer's case was a checkpoint racing a
  background backfill.
- **"The server sets `wal_autocheckpoint=0` and checkpoints by hand."** No
  server code did; the claim was withdrawn.
- **"A runtime's missing `SQLITE_DEFAULT_MEMSTATUS=0` explains its slower
  concurrent reads."** The compile option is absent from that build (checked
  with `PRAGMA compile_options` against another runtime's build of the same
  SQLite version). A plain C program shows the flag matters for threaded reads.
  No build of that runtime with the flag was run. Suspected only (U).
- **"The slow query needs rewriting."** The cause was missing statistics.
- **Ratios between stores of 84 to 563 times.** The comparison set one store at
  `synchronous=NORMAL` against stores whose setting was not recorded.

## Never measured here

- `mmap_size`, `cache_size` or `temp_store` on a database of several gigabytes.
- How long the WAL window of lost commits is under `synchronous=NORMAL`.
- How long `ANALYZE` holds locks inside a live server.
- A benchmarked connection pool, Turso or libSQL, or `sqlite-multiwriter`.
